# FAME Knowledge Agent Gateway 中文使用手册

## 1. 项目是什么

FAME Knowledge Agent Gateway 是一个 Agent 外部记忆和执行治理系统。它把知识网、项目记忆、工具调用、FAME 反馈、可视化和运行时网关合成一个可接入任何 Agent 的外部插件。

它的核心不是“搜一段资料给模型”，而是让 Agent 按工程路线工作：

```text
目标
-> 限定项目/科目/路线
-> 进入语言树和知识网
-> 做抽象与联想
-> 用 FAME 参数评估路线
-> 打包健康上下文
-> 提出工具动作
-> 网关审批
-> 执行工具
-> 记录结果、失败、证据和教训
```

适用场景：

- 长周期软件工程。
- 多 Agent 协作。
- 需要工具调用安全边界的自动化工作流。
- 需要知识网参与思考，而不只是检索的项目。
- 需要把项目落地经验沉淀为外部记忆的团队。

## 2. 核心概念

### 2.1 语言树中枢

语言树是知识网的中心。它负责把用户目标转成可执行路线，包括意图、词汇、语法、语义、表达和验证。

专业知识不应该孤立堆放，而是围绕语言树生长。这样 Agent 在处理新问题时可以先理解“这件事在语言和抽象层面是什么”，再决定要调用哪个学科、哪条路线、哪个工具。

### 2.2 FAME 路由参数

路线边使用 FAME 参数记录工程状态：

```text
mu       有效性
chi      探索价值
epsilon  与目标和语义的贴合度
kappa    置信度
nu       风险和不确定性
delta    逻辑冲突
rho      资源和上下文压力
lambda   失败教训权重
```

这些参数会随着构建、测试、工具结果、人工反馈和失败复盘更新。成功路线会变得更可信，失败路线不会被删除，而是变成教训。

### 2.3 项目记忆 Overlay

核心知识网记录通用知识。项目记忆记录某个工程的实际落地过程。

项目记忆不会直接污染核心知识网。只有经过人工或规则审核后，项目经验才可以晋升为核心知识候选。

### 2.4 工具调用治理

Agent 不能直接执行危险或变更类工具。标准流程是：

```text
ProposedAction -> ApprovedAction -> Tool Gateway -> ToolResult
```

这样可以避免模型“知道工具大概怎么用，但实际调用时参数错、路径错、权限错”的问题。

### 2.5 上下文健康

系统不把全量图谱塞进模型上下文。它按需读取：

```text
current_intent
route_summary_top_k
abstraction_summary
fame_state_summary
recent_relevant_lessons
active_constraints
```

任务结束后，完整 trace 和原始记录保留在外部存储，模型上下文只保留摘要、引用和下一步所需内容。

## 4. 环境要求

- Node.js 24 或更新版本。
- npm。

Node 24 是必须项，因为运行时网关使用 Node 内置的 `node:sqlite`。

## 5. 安装和启动

推荐一键启动：

```powershell
.\start.ps1
```

或：

```bat
start.bat
```

一键脚本会设置 UTF-8 输出，安装缺失依赖，生成索引，启动 Workbench 和 Runtime Gateway，并打开 `http://127.0.0.1:5178/`。

进入 `Agent Runtime` 后会显示首次接入向导。可以选择 `中文开源版` 或 `English open edition`，选择本机 Agent 预设或 `Other / 自定义 Agent`，复制接入消息或配置片段，等 Agent 回复后由用户确认接入。

手动方式：

安装依赖：

```bash
npm run install:all
```

生成工作台所需索引：

```bash
npm run generate:all
```

启动可视化工作台：

```bash
npm run dev
```

## 6. 工作台怎么用

### 6.1 Agent 外脑控制台

Workbench 默认进入 `Agent 外脑`。这个视图不是替代 3D/2D 图谱，而是把 Agent 运行时最关键的强制机制压成一个总控台：

- `安全阻断`：显示当前 `ProposedAction` 是否已经得到 `ApprovedAction`，红灯时不应继续调用工具。
- `动作契约审批流`：按 Scope、ContextPack、ProposedAction、ApprovedAction、ToolResultSummary、Memory Writeback 展示执行链。
- `动态免疫网`：把 SCAC 反馈、route posterior、构建/测试/工具反馈变成可观察的免疫信号。
- `失败签名热力区`：突出负值 FAME、失败教训、blocked/fail feedback，帮助 Agent 下次不要复发同类错误。
- `上下文节流`：显示本轮保留摘要、释放长日志和按需懒加载的比例。

普通用户先看 `Agent 外脑` 是否绿灯；需要配置 Agent 时点 `接入` 进入 `Agent Runtime`，需要看大局点 `3D Universe`，需要改局部路线点 `2D Detail`。

### 6.2 3D 知识宇宙

3D 图用于大局观察：

- 鼠标拖动旋转或平移。
- 滚轮缩放。
- 搜索节点、路线、知识文件、项目记忆和资产索引。
- 负值或风险更高的 FAME 路线会有明显区别。
- 双击 3D 节点进入对应 2D 局部路线图。

3D 图不追求一次展示所有底层节点，而是展示知识网的全局结构、科目聚类和路线关系。

### 6.3 2D 路线图

2D 图用于局部编辑和精细检查：

- 查看当前路线内部节点和边。
- 双击模块进入编辑。
- 在局部视窗里增加、修改、删除模块和路径。
- 查看 FAME 参数、失败教训和同步状态。

### 6.4 文字目录索引

文字目录适合按科目逐级展开。大项目图谱很容易爆炸，目录索引用来帮助用户和 Agent 快速定位位置，再进入 3D 或 2D 图查看关系。

## 7. Agent 接入方式

### 7.1 Workbench 图形化接入

Workbench 的 `Agent Runtime` 视图提供本机 Agent 傻瓜接入向导。它不自动改写用户的 Codex、Cursor、Claude Desktop 或其它 Agent 配置，而是把接入过程拆成可确认的四步：

```text
选择本机 Agent
-> 检查接入命令和必要入口
-> 复制/发送 Agent 接入消息
-> Agent 回复后由用户确认已接入
```

当前图形化预设覆盖 Codex、Cursor、Claude Desktop、Claude Code、OpenAI Agents SDK、Gemini CLI、OpenHands、SWE-agent、Aider、Cline、Roo Code、Continue、LangGraph、AutoGen、CrewAI、Dify 和 Generic Agent。没有预设的工具型 Agent 使用 `Other / 自定义 Agent`，例如 OpenClaw、Hermes、爱马仕。

向导生成的接入消息会明确要求 Agent 遵守：

- 先走语言树归一，再按 `subject / route_id` 裁剪上下文。
- 工具调用前生成 `ProposedAction`。
- 高风险动作等待 `ApprovedAction`。
- 执行后写 `ToolResultSummary`。
- PowerShell 中文乱码先走 `route-powershell-encoding-output`，不要直接判断源文件损坏。

真实检查命令仍然是：

```bash
npm run connect:chinese-open -- --agent codex
```

Workbench 卡片适合给普通用户操作确认；CLI / HTTP / MCP 适合给外部 Agent 自动接入。

### 7.2 HTTP 接入

除 `/health` 外，HTTP 请求需要 API key：

```text
Authorization: Bearer dev-fame-agent-key
```

常用端点：

```text
GET  /health
GET  /stats
GET  /agent/me
POST /goal/resolve
POST /knowledge/route
POST /context/pack
POST /action/propose
POST /tool/execute
POST /summary/write
POST /patch/submit
POST /clock/schedule
POST /semantic/search
POST /assets/sync
POST /trace/export
```

典型流程：

```text
resolve goal
-> route knowledge
-> pack context
-> propose action
-> execute tool with approval_token
-> write summary / trace / feedback
```

示例见：

```text
examples/http-client/approved-tool-call.mjs
```

### 7.3 MCP 接入

MCP 工具包括：

```text
resolve_goal
route_knowledge
pack_context
propose_action
execute_tool
write_summary
submit_patch
get_sync_status
schedule_clock
run_due_clocks
semantic_search
rebuild_semantic_index
sync_asset_index
list_assets
export_trace
```

Agent 使用 MCP 时，应遵守固定顺序：

```text
resolve_goal -> route_knowledge -> pack_context -> propose_action -> execute_tool
```

不要让 Agent 绕过审批链直接调用变更工具。

## 9. 多模态数据

知识网不直接承载重型多模态数据。推荐结构：

```text
asset database / object store
-> asset_id
-> caption / summary
-> preview ref
-> text ref
-> object ref
-> route refs
-> FAME summary
```

图谱只保存预览和索引，原始图片、音频、视频、文档留在数据库或对象存储。

手动调整知识网后，可以通过资产同步机制保持数据库索引一致。

## 10. 评测指标

建议持续跟踪：

- tool success rate：工具调用成功率。
- context token saved：上下文 token 节省量。
- failure recurrence reduction：重复失败下降率。
- route convergence：路线是否越来越接近目标。
- search scope hit rate：限定范围内搜索命中率。
- human review override rate：人工否决率。

运行烟测：

```bash
npm run gateway:smoke
```

运行完整门禁：

```bash
npm run ci
```

## 12. 常见问题

### 为什么不用普通 RAG

普通 RAG 主要解决“找资料”。本项目要解决的是“工程中如何按路线思考、调用工具、记录反馈、避免重复失败”。所以图谱、FAME、工具门禁和项目记忆是核心。

### 为什么要保留失败路线

失败路线可以作为教训。FAME 的 `lambda` 和风险参数会让 Agent 在以后遇到相似问题时避开旧坑，或者要求人工审核。

### 为什么知识网不直接存多模态原始数据

原始多模态数据太重，会让图谱难维护。图谱适合保存轻量索引、摘要、预览和引用，真正数据放在数据库或对象存储。

### 为什么需要运行时网关

大模型通常知道工具如何使用，但在真实工程里容易因为路径、参数、权限、上下文过期而出错。运行时网关把“想调用工具”和“允许执行工具”分成两步，降低误操作风险。
